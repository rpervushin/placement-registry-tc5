# Задачи по развёртыванию сервиса

Перечень задач по этапам (детальнее - в `ARCHITECTURE.md`). Порядок в MVP -
последовательный: согласование архитектуры должно быть завершено до старта разработки.

## MVP

**Согласование (до старта разработки)**
1. Утвердить решение по разработке сервиса с бизнесом
2. Пройти архитектурное согласование (арх. комитет, грумминги)

**Инфраструктура (может идти параллельно с согласованием)**

3. DevOps: подготовить инфраструктуру для развёртывания (k8s/Helm-манифесты, тестовый контур).
4. Завести репозиторий в корп. GitLab, настроить CI (lint/test) по образцу MS Catalog.

**Разработка**

5. Поднять скелет FastAPI-сервиса (routers/services/domain_services/repositories/settings) +
   Dockerfile на корп. базовом образе — пустой сервис.
6. Поднять PostgreSQL + Alembic-миграции под доменную модель (Placement, AuditLog).
7. Реализовать `internal`-эндпоинт приёма push от RecSys: входящий список актуальных
   плейсментов и их настроек, по расписанию/триггеру. Обработка - синхронно в хендлере
   (см. примечание про `arq` ниже), без исходящего HTTP-клиента к RecSys.
8. Реализовать `admin`-API: просмотр и правка конфигурации плейсментов (Read+Update; без
   Create/Delete — плейсменты появляются автоматически через push от RecSys), карта плейсментов.
9. Подключить X5ID-аутентификацию (без ролевой модели — только Администратор реестра).
10. Подключить observability (`x5d-monitoring`: логи, APM, Prometheus, health-checks).
11. Собрать Admin UI (React): конфигурация плейсмента рядом с его метриками из Grafana, карта
    полок.

**Открытое / для уточнения**

12. Зафиксировать решение по плейсментам поиска/листинга RecSys (4–6 шт., хардкод в коде
    RecProcessing, не в БД) — ожидаем от RecSys, не берём в работу до перехода RecProcessing
    с Python на Go.

## Этап 2 - Управление правилами встраивания медиа-объектов

Линия развития реестра, следующая за MVP - конфигурационный слой для встраивания
промотируемых объектов в рекомендации (см. `ARCHITECTURE.md` §10, `MEDIA_INTEGRATION.md`).
Зафиксирована как следующий этап после MVP на встрече 2026-08-27;

1. Расширить доменную модель реестра: Stakeholder, ObjectType, EmbeddingRule (приоритет +
   fallback-цепочка), DiversityRule, GlobalRule — на уровне плейсмента.
2. Реализовать `admin`-API правил встраивания: CRUD приоритета и fallback-сценарии (если не пришли от одних, показывать других),
   разрешённых типов объектов и их позиционирования (частота/интервал), правил разнообразия, глобальных настроек.
3. Реализовать эндпоинт отдачи правил потребителю - формат
   `{placement_id, stakeholders, allowed_object_types, diversity_rules, global_rules}`;
   конкретный потребитель (MS Catalog или Splitter BFF) зависит от решения по развилке (см.
   `ARCHITECTURE.md` §12 - открытый вопрос).
4. Собрать Admin UI: 5 блоков в карточке плейсмента (стейкхолдеры и приоритет с drag-and-drop,
   разрешённые типы объектов, правила разнообразия, глобальные настройки, метрики).
5. Согласовать схему получения кандидатов от стейкхолдеров в Catalog/BFF - API-push или Kafka (открытый вопрос, `MEDIA_INTEGRATION.md` §9).

## Этап 3 - Развёртывание админки

Сам backend-сервис остаётся отдельным независимо от размещения UI. Обсуждается встраивание UI
реестра в единую админку компании (контур LEGO/BDUI) вместо отдельной самостоятельной админки.
Может идти параллельно с интеграцией через Splitter BFF (открытый вопрос ниже) и с подключением
стейкхолдеров для поставки кандидатов на встраивание (`MEDIA_INTEGRATION.md` §9) — треки не
пересекаются по ресурсам.

1. Определить точку входа в единой админке (меню/маршрут) совместно с командой единой админки.
2. Определить формат встраивания: отдельный SPA на своём домене со ссылкой из единой админки, или
   интеграция компонентов в существующий фронтенд единой админки.
3. Согласовать отображение ролевой модели (Администратор реестра / Владелец полки) в контуре
   единой админки.

Оценка не дана - по итогам встречи 2026-08-27 для оценки нужны фронтенд-ресурсы, которых пока нет
в команде.

## Открытый вопрос — MS Catalog vs Splitter BFF

Где происходит слияние рекомендаций RecSys, правил встраивания из реестра и кандидатов
стейкхолдеров — в MS Catalog (расширение `/context`) или в Splitter BFF (новая ручка
`/placement`). Подробности и таблица сравнения — `ARCHITECTURE.md` §12.

Статус на 2026-08-27: решение не принято. Для MVP предварительно рассматривается вариант с
Catalog, с возможным переездом на Splitter BFF позже. Нужна отдельная встреча с командами Splitter
BFF и LEGO.

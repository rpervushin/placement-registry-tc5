# Реестр плейсментов: правила встраивания объектов от стейкхолдеров

**Версия:** 0.4  
**Дата:** 2026-08-07  
**Скоуп:** товарные листинги с рекомендациями (бесконечная лента, листинги категорий).

---

## Как это работает: кратко

Рекомендательный листинг в МП - это не только товары от RecSys. В него встраиваются объекты от нескольких стейкхолдеров: X5 Media (Реклама), Маркетинг, Контент. Каждый стейкхолдер присылает свои объекты, затем Catalog или BFF-сервис встраивает их в листинг по правилам, которые сообщает реестр.

**Последовательность работы:**

1. Стейкхолдеры заблаговременно поставляют своих кандидатов для встраивания в Catalog или BFF (в зависимости от итогового арх. решения). X5 Media (Реклама) отправляет объекты в в момент каждого запроса пользователя через AdSDK (аукцион в реальном времени).
2. В реестре настраиваются правила плейсмента: какие типы объектов разрешены, приоритет между стейкхолдерами, как часто встраивать каждый тип, что делать при отсутствии контента.
3. Ключевой сервис (Каталог или BFF) раз в час забирает актуальные правила из реестра и сохраняет их локально. 
Реестр не задействован при каждом запросе пользователя - скорость приложения не меняется.
4. При запросе пользователя Catalog запрашивает товары у RecSys по контекстной ручке. Объекты X5 Media у AdSDK (таймаут 100 мс). Кандидаты от остальных стейкхолдеров уже в кэше.
5. При формировании итогового ответа применяются правила из реестра: расставляются объекты по позициям с учётом приоритета стейкхолдеров, типа объекта и правил разнообразия. Итоговый ответ - товары + встроенные объекты - уходит в МП.

## 1. Контекст и проблема

Несколько стейкхолдеров хотят встраивать свои объекты в рекомендательные листинги МП ТС5: X5 Media (Реклама), Маркетинг, Контент. Правила встраивания сейчас разбросаны по коду и BT-документам.

Изменить любое правило — значит вносить правки в код Catalog и делать деплой. Никто не видит всех правил разом. Стейкхолдеры не понимают, что разрешено в каждом плейсменте. Нет возможности настраивать приоритет между стейкхолдерами без разработки.

**Цель:** реестр становится единым местом, где продакт может управлять правилами встраивания для каждого плейсмента — без деплоя, через UI.

---

## 2. Стейкхолдеры и модель поставки контента

В рекомендательные листинги встраиваются объекты от нескольких стейкхолдеров. Они различаются по типу поставки контента:

| Стейкхолдер | Как поставляет контент | Примеры объектов |
|---|---|---|
| **X5 Media (Реклама)** | Realtime — Catalog запрашивает AdSDK при каждом запросе пользователя. Аукцион в реальном времени | Медиабаннер, видео-баннер, спонсированная карточка товара |
| **Маркетинг** | Pre-cached — объекты заранее поставлены в Catalog | Карусель товаров из pBase, баннер |
| **Контент** | Pre-cached — объекты заранее поставлены в Catalog | Редакционные подборки, полки |
| **Рецепты** | Pre-cached — отдельный сервис и команда, не часть Контента (уточнено 2026-08-27) | Карточки рецептов |
| **Трейд-промо** | Pre-cached | Акционные товарные подборки |

Реестр хранит **приоритет между стейкхолдерами** для каждого плейсмента: чей контент показывается первым, кто является fallback если приоритетный стейкхолдер не прислал объекты.

Стейкхолдеры **не имеют доступа к управлению правилами** — они только поставляют контент. Приоритеты и правила встраивания настраивает только admin реестра (команда Каталога).

---

## 3. Типы встраиваемых объектов

Каждый тип объекта имеет свою логику позиционирования в листинге:

| Тип | Логика позиции | Пример правила | Статус |
|---|---|---|---|
| `media_banner` | Тайловая — занимает одну плитку в сетке товаров | Каждая 5-я плитка | MVP |
| `product_card` | Тайловая — спонсированная карточка товара, визуально как обычная плитка | Каждая 5-я плитка | P1 |
| `video_banner` | Тайловая — автовоспроизведение без звука | Каждая 5-я плитка | Бета |
| `product_carousel` | Строчная — разрывает сетку, занимает всю ширину экрана | Не раньше 3-й строки, далее каждые N строк | P1 |
| `recipe` | Тайловая — карточка рецепта в сетке товаров | Каждая 10-я плитка | P2 |
| `stub_banner` | Тайловая — системный fallback, всегда активен | — | Всегда |

**Важное различие:** тайловые объекты позиционируются по номеру плитки (5, 10, 15…), строчные объекты — по номеру строки (3-я строка, каждые 5 строк). Смешивать их в одном правиле нельзя — реестр хранит тип позиционирования для каждого разрешённого объекта отдельно.

---

## 4. Правила разнообразия

Два уровня ограничений на повторяемость встраиваемых объектов:

**Уровень 1 — не два объекта от одного стейкхолдера подряд** (рекомендуется всегда включать). Даже если у Рекламы 5 объектов, а у Маркетинга 1 — система чередует их, не ставит два объекта одного стейкхолдера подряд. Защищает от монополизации ленты.

**Уровень 2 — не два объекта одного типа подряд** (опционально). UX-правило: карусель не идёт сразу за каруселью, даже если они от разных стейкхолдеров.

Оба ограничения настраиваются per-placement. Если при соблюдении обоих нельзя выбрать следующий объект — система сначала расслабляет ограничение по типу (мягче), затем по стейкхолдеру (жёстче).

Набор объектов и порядок их встраивания не фиксируются жёстко: реестр задаёт правила «что разрешено и как часто», а Catalog встраивает то, что прислали стейкхолдеры, в соответствии с этими правилами и приоритетами.

## 5. Первый кандидат: `main.endless_recommendation`

Бесконечная рекомендательная лента на Главной ТС5 (MOBILE-2577).

### Что реестр хранит для этого плейсмента

> Для `main.endless_recommendation` в приоритетной цепочке пока настроены три стейкхолдера (X5 Media, Маркетинг, Контент); позиция «Рецептов» и «Трейд-промо» в этой цепочке — открытый вопрос (см. §9).

```yaml
placement_id: "main.endless_recommendation"
placement_type: "recommendation_listing"
screen: "home"
owner_team: "Каталог"
status: active

# Стейкхолдеры и их приоритет
stakeholders:
  - key: x5_media
    name: "X5 Media (Реклама)"
    priority: 1
    delivery_mode: realtime          # запрашивается при каждом запросе пользователя
    delivery_config:
      ad_sdk_slot_id: "main_endless_rec_v1"
      timeout_ms: 100
    fallback_to: marketing
  - key: marketing
    name: "Маркетинг"
    priority: 2
    delivery_mode: pre_cached        # кандидаты заранее загружены в Catalog
    fallback_to: content
  - key: content
    name: "Контент"
    priority: 3
    delivery_mode: pre_cached
    fallback_to: null                # конец цепочки fallback

# Разрешённые типы объектов и правила их позиционирования
allowed_object_types:

  - type: media_banner
    label: "Медиабаннер"
    positioning: tile
    frequency: 5                     # каждые 5 плиток
    max_per_scroll: 1
    repeat_min_interval: 10          # повтор не раньше чем через 10 плиток
    allowed_stakeholders: [x5_media]

  - type: product_card
    label: "Спонсированная карточка товара"
    positioning: tile
    frequency: 5
    allowed_stakeholders: [x5_media, marketing]

  - type: product_carousel
    label: "Карусель товаров"
    positioning: row                 # разрывает сетку, занимает всю строку
    first_occurrence_after_rows: 3   # первая — не раньше 3-й строки
    repeat_interval_rows: 5          # далее — не чаще каждых 5 строк
    allowed_stakeholders: [marketing, content]

  - type: recipe
    label: "Рецепт"
    positioning: tile
    frequency: 10                    # не чаще каждой 10-й плитки
    allowed_stakeholders: [recipes]   # уточнено 2026-08-27: "Рецепты" - отдельный стейкхолдер, не "Контент"

  - type: video_banner
    label: "Видео-баннер"
    positioning: tile
    frequency: 5
    beta: true
    allowed_stakeholders: [x5_media]

  - type: stub_banner
    label: "Заглушка"
    always_active: true              # системный тип, не редактируется

# Правила разнообразия
diversity_rules:
  no_consecutive_same_stakeholder: true
  no_consecutive_same_type: true

# Глобальные настройки
global_rules:
  max_embedded_per_scroll: 2
  fallback_behavior: fill_with_product

# Включение/выключение слотов (feature-тоглы)
feature_toggles:
  slot_5: true
  slot_10: true
  slot_15: true
  slot_20: false
  slot_25: true

# Метрики (read-only, из Grafana)
metrics:
  tracked: [ctr, fill_rate, stub_rate, revenue_per_1k_sessions, viewability]
```

## 6. Как правила применяются в приложении

Реестр — инструмент управления конфигурацией, не сервис реального времени. Он не задействован при каждом запросе пользователя.

**Фоновое обновление — раз в час:**
```
MS Catalog → Реестр: запросить правила всех плейсментов
← Реестр возвращает: {placement_id, stakeholders, allowed_object_types, diversity_rules, ...}
MS Catalog сохраняет правила в локальный кэш (Redis)
```

**При каждом запросе пользователя:**
```
МП → MS Catalog: открыть экран с рекомендациями

  параллельно:
    1. RecSys → персонализированные товары
    2. X5 Media AdSDK → объекты реального времени (таймаут 100 мс)

  из кэша Catalog:
    - кандидаты от Маркетинга (pre-cached)
    - кандидаты от Контента (pre-cached)
    - правила встраивания из реестра

  Catalog применяет правила:
    → приоритет стейкхолдеров
    → тип позиционирования (тайловый / строчный)
    → частота и интервалы
    → правила разнообразия (no-consecutive)
    → fallback-цепочка при отсутствии объектов

МП ← MS Catalog: единый ответ — товары + встроенные объекты на нужных позициях
```

Если правило обновлено в реестре, оно применится в Catalog в течение ~1 часа (следующий плановый цикл). В перспективе - мгновенное применение через Kafka.

## 7. Что нужно в Admin UI реестра

В карточке плейсмента — раздел **«Правила встраивания»** с пятью блоками:

**Стейкхолдеры и приоритет** — упорядоченный список стейкхолдеров, drag-and-drop для изменения приоритета, настройка fallback-цепочки. Видно какой стейкхолдер поставляет контент реально, какой — в режиме кэша.

**Разрешённые типы объектов** — для каждого типа: включён/выключен, от каких стейкхолдеров принимается, правила позиционирования (частота, интервал, min_rows для строчных объектов).

**Правила разнообразия** — два тогла: no-consecutive по стейкхолдеру и по типу.

**Глобальные настройки** — max объектов на скролл, fallback-поведение.

**Метрики по плейсменту** — CTR, fill rate, stub rate (read-only, из Grafana).

## 9. Открытые вопросы

**Как стейкхолдеры поставляют кандидатов в Catalog.** Пока не определён механизм: API-push, Kafka, ручная загрузка через UI. Это влияет на то, как быстро новые объекты от Маркетинга или Контента появятся в листинге.

**Привязка кандидатов к плейсментам.** Стейкхолдер присылает объект для конкретного `placement_id` или отдаёт общий пул, из которого Catalog сам выбирает подходящие? Пока открытый вопрос.

**Мгновенное применение фича-тоглов.** Сейчас - задержка до 1 часа. Если нужно быстрее (экстренное выключение слота) - опционально через Kafka, в перспективе.

**Ранжирование баннеров через Блендер** — вне скоупа. Зона ответственности RecSys, отдельная инициатива.

**Приоритет стейкхолдеров «Рецепты» и «Трейд-промо».** Типы объектов и способ поставки контента определены (§2-3), но их позиция в приоритетной цепочке для `main.endless_recommendation` (§5) пока не задана — требует продуктового решения.
